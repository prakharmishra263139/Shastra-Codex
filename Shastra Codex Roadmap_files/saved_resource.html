Shastra Codex Roadmap

Build Roadmap  /  v1

Shastra Codex

A browsable, comparable encyclopedia of Indian defence equipment — built so an SSB aspirant can walk into the personal interview knowing what a system is, what it does, and why it matters.

Scope · Equipment encyclopedia Mode · Solo, full-time Runs · Local-first Horizon · ~13 weeks to v1

Shastra Codex is a working name — swap it freely. Everything below assumes an empty folder at D:\PERSONAL\PROJECT-INFO and Node 23 already installed.

01  /  The product

One job, done extremely well

This is not an SSB prep platform. It is a reference work with a learning layer bolted on. A student lands on it because they heard "Pralay" in the news or an interviewer asked about "the difference between Akash and QRSAM", and they need a clear, trustworthy, fast answer — not a forum thread and not a 40-tab Wikipedia crawl.

Everything in the roadmap serves three verbs: find, compare, retain. If a feature doesn't serve one of those, it belongs in a later version.

Definition of done for v1

  • Any equipment reachable in under three seconds from anywhere in the app.
  • Two systems in the same class placed side by side with differences visibly marked.
  • A student can revise twenty entries in fifteen minutes without leaving the site.
  • Every specification carries a source and a last-verified date.

02  /  Technical decision

The stack, and why

You left this to me. For a content-heavy, hierarchical, comparison-driven encyclopedia that runs on your machine first and may go public later, the answer is a static-content app with no database.

Framework

Next.js 15 · App Router · TypeScript

File-based routing maps perfectly onto /missiles/air-to-air/astra. Static generation means every page is pre-rendered — instant locally, and a one-command deploy if you ever publish. Server Components keep the shipped JavaScript small.

Content store

MDX + JSON files in the repo

One file per equipment. No database to install, back up, or keep running. Git gives you version history on every spec correction. Editable in any editor. If you ever outgrow it, the same files seed a Postgres table without rewriting the app.

Validation

Zod schemas + a check script

The schema is the contract that makes comparison possible. A single npm run validate refuses to build if an entry is missing a required field, uses a wrong unit, or names a category that doesn't exist.

Interface

Tailwind CSS + shadcn/ui + Radix

You own the component source, so the aesthetic stays yours rather than looking like a template. Radix underneath gives keyboard navigation and accessibility for free — which matters for a command palette and a compare tray.

Search

MiniSearch, client-side

A prebuilt index ships with the app. Handles a few thousand entries with fuzzy matching and alias support — so "P-8", "Poseidon" and "P-8I Neptune" all land in the same place. No server, no API key.

Media

next/image + local /public

Images stay in the repo alongside content, with a mandatory credit and license field per image. Automatic resizing and lazy loading keep dense grid pages fast.

Deliberately not in v1

No user accounts, no backend, no payments, no CMS. Every one of those costs days you should be spending on content and on the compare view. Bookmarks and quiz progress live in browser storage — they can migrate to accounts later if the site goes public.

Design rule

A system can appear under exactly one class (its home), but carries tags that surface it elsewhere. BrahMos lives under Cruise Missiles, and is tagged naval, air-launched, anti-ship so it also appears when browsing those. One home prevents duplicate content; tags prevent the taxonomy from becoming a lie.

04  /  Data model

Shared fields, typed spec blocks

This is the single decision that determines whether comparison works or not. Every entry shares an identical core; the specs block changes shape by category, because a missile's range and a tank's armour thickness are not the same kind of fact.

Lock this schema early — around entry ten — because changing it after a hundred entries means a hundred rewrites. 

// content/schema.ts  — the contract every entry must satisfy

const Core = z.object({
  slug:         z.string(),              // brahmos-block-iii
  name:         z.string(),              // "BrahMos Block III"
  aliases:      z.array(z.string()),     // ["PJ-10"] — feeds search
  category:     Category,                // missiles | armour | artillery | ...
  class:        z.string(),              // cruise-missile
  tags:         z.array(z.string()),

  origin:       z.array(z.string()),     // ["India", "Russia"]
  developer:    z.array(z.string()),     // ["DRDO", "NPOM"]
  manufacturer: z.array(z.string()),     // ["BrahMos Aerospace"]
  operators:    z.array(Service),        // army | navy | airforce | coastguard

  status:       z.enum(["in-service", "trials", "development",
                        "ordered", "retired"]),
  inducted:     z.number().optional(),   // year — drives the timeline view
  quantity:     Estimate.optional(),     // numbers are rarely official

  summary:      z.string().max(280),   // the one line shown on cards
  specs:        SpecBlock,               // ← discriminated by category

  ssb: z.object({
    whyItMatters: z.string(),            // the interview angle
    hooks:        z.array(z.string()),   // memory aids: "Fastest cruise missile in service"
    likelyAsked:  z.array(z.string()),   // real PI-style questions
    confusedWith: z.array(z.string()),   // slugs — auto-builds a compare shortcut
  }),

  sources:      z.array(Source).min(1),  // url + publisher + accessed date
  lastVerified: z.string().date(),       // shown on the page. Non-negotiable.
});

// Per-category spec blocks — this is what makes side-by-side comparison honest
const SpecBlock = z.discriminatedUnion("category", [

  /* missiles  */ z.object({ category: z.literal("missiles"),
      range: Measure, speed: Measure, warhead: Measure, guidance: z.array(z.string()),
      length: Measure, diameter: Measure, launchWeight: Measure,
      propulsion: z.string(), platforms: z.array(z.string()) }),

  /* armour    */ z.object({ category: z.literal("armour"),
      weight: Measure, crew: z.number(), mainGun: z.string(), ammoCarried: z.number(),
      enginePower: Measure, topSpeed: Measure, operationalRange: Measure,
      armourType: z.string(), fireControl: z.string() }),

  /* aircraft  */ z.object({ category: z.literal("aircraft"),
      role: z.string(), crew: z.number(), maxSpeed: Measure, combatRadius: Measure,
      serviceCeiling: Measure, payload: Measure, hardpoints: z.number(),
      engines: z.string(), radar: z.string() }),

  /* naval, artillery, smallarms, airdefence, sensors — same pattern */
]);

// Defence figures are contested. Model that instead of pretending otherwise.
const Measure = z.object({
  value:      z.number(),
  unit:       z.string(),                // km | m/s | kg | mm | hp
  confidence: z.enum(["official", "reported", "estimated"]),
  note:       z.string().optional(),     // "290 km for export variant"
});

Why confidence earns its place

Half of publicly available defence specifications are estimates or export-variant figures. A site that prints them as hard fact will eventually mislead a candidate in an interview. Render official plainly, reported and estimated with a small marker and a tooltip. That single detail is what will separate this from every scraped listicle site.

Comparison then falls out for free: two entries with the same category share a spec shape, so the compare table is a generic diff over the same keys. Cross-category comparison is disabled by design — comparing a frigate to a rifle produces a table of blanks.

05  /  Interface

Navigation, entry page, compare

You asked for professional, smooth, aesthetic, and easy to compare. That resolves into four specific pieces of interface, in this order of importance.

Piece one · Navigation shell

Persistent tree, always-available search

A left rail holding the category tree, collapsed to the current branch, present on every page so the student never loses their place. Breadcrumbs across the top (Missiles / Cruise / BrahMos). A command palette on Ctrl-K that searches names, aliases and summaries and is the fastest path to anything. On mobile the rail becomes a sheet.

Piece two · Entry page anatomy

The same shape, every single time

Predictability is the feature. A student who has read three entries should know exactly where to look on the fourth.

HeroName, service badges, status pill, origin flag, primary image
At a glanceFour to six headline stats as large tabular figures — the numbers an interviewer actually asks for
SummaryTwo paragraphs: what it is, what problem it solves
SpecificationsFull typed table with confidence markers and units
VariantsHorizontal timeline of blocks and marks, with what changed at each step
In serviceOperators, platforms it launches from or carries, deployment notes
SSB angleWhy it matters, memory hooks, likely questions, systems it is confused with
Compare withAuto-generated from confusedWith plus same-class siblings
SourcesCitations and last-verified date

Piece three · Comparison

A tray that follows you, a table that shows the delta

A compare button on every card and entry page adds the item to a docked tray at the bottom of the screen, up to four items. Opening the tray produces a side-by-side table where identical values are dimmed and differing values are emphasised, with the strongest figure in each numeric row marked. Rows can be filtered to differences only. The comparison state lives in the URL, so a specific comparison is a shareable, bookmarkable link.

Piece four · Learning layer

What turns a database into study material

  • Revision list — star any entry; a dedicated page collects them.
  • Flashcard mode — generated automatically from spec fields and memory hooks. No separate authoring.
  • Quick quiz — multiple choice built by pulling the correct value and three wrong ones from sibling entries in the same class. Zero content cost, high study value.
  • One-pager — a print stylesheet that renders any entry as a clean single-sheet PDF.
  • Recently viewed — a strip on the home page so a session resumes where it stopped.

Visual direction

Technical, not tactical

Resist camouflage patterns, stencil fonts and terminal-green. The reference points that read as serious are aviation manuals, instrument panels and engineering drawings: a restrained cool-grey ground, one confident accent, a technical sans for headings, a monospace for every number so columns align. Dark mode first, since students study at night, with a proper light mode rather than an inversion. Motion limited to what communicates — the compare tray sliding, a value counting into place — never ambient decoration.

06  /  Execution

Eight phases to v1

Sequenced for one person working full-time. Durations are guides, not commitments — the done when line is the real gate. Phase 5 runs in parallel with everything after Phase 3, because content is the long pole and cannot wait until the app is finished.

0Days 1–4

Foundation and vertical slice

Prove the whole pipeline end to end on a single entry before building breadth.

  • git init, Next.js + TypeScript + Tailwind scaffold, shadcn/ui installed
  • Design tokens committed: colour scale, type scale, spacing, dark and light
  • Taxonomy written as a single taxonomy.ts file
  • One hand-written entry (BrahMos) rendering at its real route through the real layout

DONE WHEN  /missiles/cruise/brahmos renders from a content file, in both themes, on desktop and phone.

1Week 1–2

Data model and content engine

Make adding an entry a five-minute job rather than a copy-paste ritual.

  • Zod schemas for core plus the first four category spec blocks
  • Content loader with build-time parsing and typed access
  • npm run validate — fails loudly on missing fields, bad units, unknown categories
  • npm run new — a scaffolder that prompts for category and writes a pre-filled stub
  • Ten seed entries spanning three categories, to stress the schema while it is still cheap to change

DONE WHEN  a new entry goes from idea to live page in under five minutes, and a malformed entry cannot reach the build.

2Week 2–3

Browse and navigation

Everything findable, from three different directions.

  • Category and class routes with card grids, sorting, and pagination
  • Filter panel: service, origin, status, manufacturer, induction decade, numeric ranges
  • Sidebar tree, breadcrumbs, mobile navigation sheet
  • Command palette with MiniSearch over names, aliases and summaries
  • Home page: categories, recently added, recently viewed

DONE WHEN  any seeded entry is reachable within three seconds by browsing, filtering, or search.

3Week 3–5

Entry page and comparison

The two screens the whole product is judged on.

  • Full entry template — every zone from the anatomy above
  • Image pipeline with mandatory credit and licence metadata
  • Variants timeline component
  • Compare tray, up to four items, persisted in the URL
  • Side-by-side table with difference highlighting and a differences-only filter
  • Related and confused-with sections wired to the schema

DONE WHEN  Akash and QRSAM can be placed side by side and the meaningful differences are obvious in under ten seconds.

4Week 5–6

Learning layer

Convert a reference site into something a student returns to daily.

  • Revision list and starred entries in browser storage, with a dedicated page
  • Flashcard mode generated from spec fields and memory hooks
  • Auto-generated multiple-choice quiz per class, with a score summary
  • Print stylesheet producing a clean one-page PDF per entry
  • Progress indicators: entries viewed per category

DONE WHEN  twenty starred entries can be revised in fifteen minutes without leaving the app.

5Week 3–12

Content scale-up  // runs in parallel

The real work. Start the moment the schema is locked, not when the app is finished.

  • Tier 1 — 60 entries. The systems actually asked about in interviews: Agni series, BrahMos, Akash, S-400, Tejas, Rafale, Su-30MKI, Prachand, Arjun, T-90, K9 Vajra, ATAGS, Pinaka, INS Vikrant, Arihant, Kalvari, P-8I, AK-203, Nag, Rudram.
  • Tier 2 — to 150. Complete every class so no category looks abandoned.
  • Tier 3 — to 300+. Depth, variants, retired systems, foreign comparators.
  • Target roughly four to six finished entries per working day once the template is settled.
  • Weekly pass: check lastVerified dates and fold in new inductions.

DONE WHEN  Tier 1 is complete and every one of those entries has sources, an image, and a filled SSB angle.

6Week 12–13

Polish, performance, accessibility

The difference between "a project" and "a product".

  • Loading, empty and error states for every route; a real 404
  • Keyboard navigation throughout; visible focus; screen-reader labels on every icon control
  • Image optimisation pass; Lighthouse above 95 on performance and accessibility
  • Motion audit — remove anything decorative; honour reduced-motion
  • Cross-checking pass on fifty random specs against sources

DONE WHEN  you can hand the laptop to a friend preparing for SSB and they need no explanation to use it.

7Later

Optional — take it public

Only once Tier 1 content is done. A thin site launched early gets no second chance at a first impression.

  • Deploy to Vercel; buy a domain
  • SEO groundwork: per-entry metadata, structured data, sitemap, Open Graph cards generated per entry
  • Analytics and a correction-report button on every page
  • Only then consider accounts, cross-device sync, and a community layer

DONE WHEN  an organic search for a specific system brings a stranger to your page.

07  /  Content discipline

Sourcing rules, set once

Content is where this project succeeds or quietly dies. Two rules protect it.

Public sources only. Everything an SSB interview tests is openly published — Press Information Bureau releases, Ministry of Defence year-end reviews, DRDO, HAL, BEL and BDL product pages, the three service websites, and established defence journalism. That is more than enough. Do not chase leaked, classified or restricted material: it is not needed, it is not legal to republish, and it destroys the credibility the site depends on.

Every entry cites and dates itself. One source minimum, a lastVerified date rendered on the page. When a figure is disputed, show the range and mark the confidence rather than picking one and sounding certain.

Images

The easiest thing to get wrong. Use PIB and Ministry of Defence photographs under the Government Open Data Licence – India, or Wikimedia Commons files with their attribution preserved. Store credit and license as required fields so the validator refuses an uncredited image. Where nothing usable exists, a clean vector silhouette often reads better than a poor photograph anyway.

08  /  Risk register

What actually kills projects like this

RiskLevelMitigation
Content burnout at entry 40 High Ship sixty excellent entries rather than three hundred thin ones. Fix a daily quota you can hit on a bad day and stop when you hit it.
Schema churn after mass authoring High Lock the schema at ten entries. After that, changes ship with a migration script — never a hundred manual edits.
Scope creep into full SSB prep High Psychology tests, GTO tasks and mock interviews are a different product. Keep a parked-ideas file and put them in it.
Polishing the interface before content exists Medium Phase 5 starts in week 3 on purpose. An empty beautiful site is worth less than a plain full one.
Specifications going stale Medium lastVerified on every entry; a build warning past twelve months; a weekly review slot.
Image licensing problems Medium Required credit and licence fields enforced by the validator, from the very first image.
Publishing an incorrect figure Medium Confidence markers, visible sources, and a correction-report control once the site is public.

09  /  Start here

The first four moves

Everything above is planning. These are the things to do today.

Write the taxonomy file before writing any code

Every category, every class, final slugs. An hour spent here saves a week of renaming routes later.

Hand-write three entries in a plain text file

A missile, a tank, and a fighter. Written as prose and figures, no schema yet. The fields you naturally reach for are the schema.

Build the vertical slice — Phase 0

One entry, one real route, real layout, both themes. Do not start a second entry until the first page looks like something you would show a friend.

Lock the schema and start Tier 1 content

From week three, content runs every single day alongside whatever feature you are building.

The one sentence to keep

Sixty systems covered properly — sourced, dated, compared, with the interview angle written out — is a genuinely useful study tool. Three hundred half-filled stubs is a database nobody trusts. Build the first one.
